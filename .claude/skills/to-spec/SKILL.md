# Спека из решений

Спека **записывает уже принятые решения** и не порождает новых. Всплыл нерешённый вопрос —
сними его скиллом `discuss` (протокол в `docs/discussions/`) и вернись сюда. Решения
wayfinder-карты (`bd show <карта>` → Decisions so far, закрытые тикеты карты) — полноправный
вход: не переспрашивать.

**Один файл, две части.** Первой идёт человеческая (её читает владелец), затем черта `---`,
затем агентная (её читают исполнители и ревьюеры). **Решение живёт ТОЛЬКО в человеческой части
и имеет номер; агентная ссылается номером и не пересказывает** — правило машинно проверяет
`scripts/spec-check.py` последним шагом. Перенесено из workwatch (форма 2, раздел C).

## Шаги

### 1. Прочитай затронутый код и решения

Пройди по модулям, которых коснётся работа, по ADR в `docs/adr/` и по закрытым тикетам карты.
Термины бери из `CONTEXT.md` (Запись, Заметка, Кнопка, Пайплайн, Очередь, Задача, Реестр…);
двусмысленный термин правь в `CONTEXT.md` тем же ходом.
**Готово:** назван список затронутых слоёв (приложение / GitHub Action / формат репо заметок / STT).

### 2. Сверь строку `ADR:`

ADR пишет скилл `adr` на шаге ADR-гейта стадии `discuss`, здесь только сверка. Гейт сработал
(список тем — `CLAUDE.md` → _ADR-гейт_), а ADR нет — вернись в `adr` и напиши его.
**Готово:** в шапке спеки есть строка `ADR:` — путь к файлу или «не затронут».

### 3. Наметь seams

Seam — публичная граница, через которую пишется тест. Предпочитай существующую новой, бери
самую высокую, целься в одну (образцы: порт `GithubApi` с фейком, `Edit.apply(text, edit)`,
`TranscriptMapper.fromDeepgramJson`, экраны через семантику Compose). Решение принимай здесь и
записывай в спеку: она придёт владельцу на апрув пачкой вместе с планом.
**Готово:** каждая граница названа модулем и помечена «существующая» или «новая».

### 4. Напиши человеческую часть

`docs/specs/<ГГГГ-ММ-ДД>-<слаг>.md`, по-русски, **не длиннее 60 строк**, языком скилла
`wait-what` — без слов «компонент», «воркер», «рефактор». Порядок:

| Блок | Что в нём |
|---|---|
| Шапка | Дата, Статус (`черновик` до подписи владельца), `ADR:`, `Эпик:`, `Карта:` (если есть) |
| Зачем | Что не работает у владельца, его словами |
| Пример на настоящих данных | Строка его заметки — имя, дата, фраза из транскрипта — и что он увидит после работы |
| `## Решение N` | Заголовком на каждое решение, номер сквозной; в конце блока строка «Увидишь: …» — наблюдаемое поведение |
| Чего НЕ будет | Что рядом и не делается — пункт на каждое ожидание, которое иначе достроят |
| Что нужно от владельца | Подпись, развилка, регистрация в сервисе, действие на телефоне — или «ничего» |
| Журнал правок | Пустой до подписи; после — строкой «дата — что — кто попросил» |

**Готово:** человеческая часть ≤ 60 строк, каждое решение стоит под своим `## Решение N` и
несёт строку «Увидишь: …», заполнены все блоки таблицы.

### 5. Напиши агентную часть

Ставь черту `---` после последнего решения и пиши то, чего в человеческой части быть не должно.
У каждого блока — проверяемый критерий, не пожелание:

| Блок | Что в нём |
|---|---|
| Критерии приёмки | «действие → наблюдаемый результат», каждое решение покрыто и названо номером |
| Затронутые слои | Таблица: приложение / Action / формат репо / STT; слои, которые НЕ меняются, — тоже строкой |
| Seams | Из шага 3, каждый с меткой «существующая» / «новая»; что здесь хороший тест, прецеденты в `app/src/test/` |
| **Замороженные контракты** | Форма frontmatter, имена файлов, параметры запроса STT, промпт Action — до нарезки срезов. Единственное место, где куски кода живут в спеке: их нельзя переоткрывать |
| Бюджеты | Числами: время от «стоп» до заметки в GitHub; запросов к API на запуск и на жест (лимит 5000/ч — но и один лишний запрос на каждое обновление недопустим, срез Н7); размер транскрипта, который экран обязан выдержать; батарея/фон, если затронут сервис записи |
| Проверка на стенде | Три пункта именем: **смоук на тестовом репо** `Roflochinsky/voice-notes-test` (какой тест-смоук и какой переменной включается); **прокликка на телефоне** — что открыть, что нажать, что увидеть (делает владелец, телефон не стенд); **сверка с артефактом дизайна** — `DESIGN.md` плюс утверждённый комп из `docs/design/`, что сверяется |
| Архитектура (HLD) | **Обязателен при 2+ слоях**: компоненты, потоки данных, контракты между слоями |
| Указатели | Пути к плану, ADR, `DESIGN.md`, компу — каждый проверен `test -f` |

Пути файлов и куски кода вне блока «Замороженные контракты» держи вне спеки — они протухают.
«Должно работать быстро» — не бюджет; спека без числа не заполнена.

**Готово:** каждый блок заполнен, ни одного «TBD», и три самопроверки прошли:
1. **Непротиворечивость** — два решения не требуют разного от одного места; расходятся —
   назови конфликт владельцу, а не усредняй.
2. **Двусмысленность** — каждую фразу, допускающую два прочтения, перепиши в одно.
3. **Согласованность имён** — одно понятие названо одним словом во всей спеке и в `CONTEXT.md`.

### 6. Прогони `spec-check` и свяжи с эпиком

```bash
scripts/spec-check.py docs/specs/<файл>.md   # код 0
```

Отказы читай буквально: «решение не упомянуто в агентной части» — его никто не реализует;
«абзац пересказан дословно» — вынеси ссылку на номер вместо копии. Затем положи путь спеки в
описание bd-эпика; эпика ещё нет — впиши путь при заведении срезов скиллом `to-tickets`.
**Готово:** `scripts/spec-check.py` вернул 0, `bd show <эпик>` печатает путь спеки.
