## 1. Блокер оси СТАНДАРТЫ НН8 — `clearReason` на повторяемой ветке. **Закрыт**

**Что видит тест.** Открыл `TranscribeWorkerTest::перегрузка и сбой вендора — retry, устаревшая
причина снята` (`TranscribeWorkerTest.kt:99-114`). На каждом из четырёх кодов (408, 429, 500, 503)
он: заводит каталог с аудио → **кладёт в него настоящую протухшую причину**
`"ошибка ElevenLabs 404\nнет такого пути"` (константа `STALE_REASON`) → зовёт
`TranscribeWorker.transcribeNote` с `stt`, бросающим `SttError(code, "busy")` → сверяет, что
результат `retry()` **и что файла `status.txt` больше нет**. Это ровно сценарий находки: «404
лежит, вендор ответил 429, экран продолжает называть 404».

**Единственность пути удаления — проверил по прод-коду.** В этом прогоне `stt` бросает до всякой
записи, поэтому `writeAtomic(TRANSCRIPT_JSON, …)` не исполняется, ветка удачи и ветка фатального
кода не заходят. Файл причины может исчезнуть только одним способом — `clearReason(dir)` в ветке
нефатального `SttError` (`TranscribeWorker.kt:139-142`). Сотри строку — файл переживёт попытку, и
`assertFalse` красный. Мерило появилось.

**Бьёт ли `M14` именно в эту строку, а не в соседнюю.** Да, и это проверяемо, а не на слово.
`find` мутации включает `} else {` перед `clearReason(dir)`:

```
                } else {
                    clearReason(dir)
                    WorkResult.retry()
                }
```

Соседний `clearReason(dir)` живёт в `catch (e: IOException)` и такого префикса не имеет. Посчитал
вхождения `find` в файле программой — **ровно одно** (строка `} else {` в файле встречается дважды,
но целиком блок — один). Значит `M14` снимает снятие причины только на повторяемом коде вендора,
а обрыв сети (его держит соседний тест `сетевой сбой — retry, устаревшая причина снята`) не
затрагивает. Прогон: `M14 … убита` тем самым тестом.

**Прод-код круг не менял** — строка была верной, не хватало стража. Согласен: правка в тесте и
есть правильный ответ на находку класса `t`.

## 2. Сужение отмены (СТАНДАРТЫ НН6 = моя Н6). **Закрыта**

`NotesStore.clearStatus` (`NotesStore.kt:84`) — `File(dir, STATUS).delete()`, то есть одним

предписал ведущий, и оно закрывает сценарий моей Н6: у идущей прямо сейчас заливки 48 МБ файла
причины нет, поэтому повторное сохранение неизменённого ключа её не рвёт.

**Держит ли тест ОБА случая — да, но двумя тестами, а не одним.** Открыл оба:

- **с причиной** — `MainActivityTest::после ввода ключа протухшая причина снята, а висящая цепочка
  отменена до постановки` (`:88-103`): `record(..., status = "нет ключа ElevenLabs")`, после вызова
  сверяет, что файла причины нет, и что лог фейков — ровно
  `["отменить 20260907-101500", "в очередь 20260907-101500"]` (порядок в списке — часть
  требования);

  `["в очередь 20260907-101500"]`, то есть отмены нет вовсе.

Разделение на два теста считаю верным решением, а не размазыванием: свали их в один — одна подмена
валила бы обоих, и по падению не понять, что именно сломано.

**Мутация `M15`.** `find` — тот же `if (…) { cancel(id) }`, вхождение в файле **одно** (проверил
программой); `replace` — безусловные `clearStatus` + `cancel`, то есть **в точности прежнее
поведение круга фикса**. Это «ближайшая неверная семантика», а не поломка: под ней тест «с
причиной» остаётся зелёным (отмена там и должна быть), падает ровно тест «без причины». Прогон
подтверждает: `M15 … убита (MainActivityTest::запись без причины только ставится в очередь…)`.
Разделяющая.
