## Модульная раскладка (LLD)

Чистое (JVM-юниты, без Android и сети) отдельно от адаптеров:

```
pipeline/
  TaskFile.kt      чистый  разбор/сборка задачи, подзадачи, имя файла (слаг+коллизии)
  NoteFile.kt      чистый  разбор/сборка заметки; DoneNoteParser — тонкая обёртка над ним
  Registry.kt      чистый  projects.md / people.md
  Edit.kt          чистый  sealed Edit + apply(text, Edit) — смысловая единица правки
  ConflictRule.kt  чистый  трёхсторонний resolve(base, mine, theirs)
  RepoDelta.kt     чистый  compare → действия над кэшем (в т.ч. renamed и «нужен пересбор»)
  BatchPlan.kt     чистый  changes → payload'ы blobs/tree/commit
  Migration.kt     чистый  plan(notes) → List<Change>
  NoteRef.kt       чистый  тождество «локальная запись ↔ путь в репо»
  GithubApi.kt     порт    readRef/readTree/readBlob/readFile/compare/put/delete/commitBatch
  GithubClient.kt  адаптер боевая реализация порта (java.util.Base64, кодирование пути)
  RepoCache.kt     адаптер files/repo/: тексты + карта путь→sha + lastCommitSha + pending
  WriteQueue.kt    адаптер files/repo/queue/: журнал операций, drain-воркер
  RepoStore.kt     фасад   ЕДИНСТВЕННАЯ точка для UI: списки, правки, удаление, статус синка
ui/
  TaskFilter.kt    чистый  фильтрация, сортировка, счётчики для чипов (today параметром)
  TasksScreen.kt · TaskDetailScreen.kt · FilterChips.kt · DeleteDialog.kt — по компу
  FeedScreen.kt · DetailScreen.kt — расширяются
```

### Решения LLD (не переоткрывать в исполнении)

1. **Единица записи — смысловая правка, не текст файла.** `sealed interface Edit`
   (SetField, SetSummary, ToggleSubtask, AddSubtask, Create, Delete) + чистый
   `apply(text, Edit)`. Очередь хранит `Edit` + `baseBlobSha`, а не готовый текст: это даёт
   и переигрывание на 409, и склейку операций, и трёхсторонний конфликт.
2. **`ConflictRule.resolve(base, mine, theirs): Merged | Divergence(fields)`** — вход
   разобранными структурами. Подзадачи сопоставляются по нормализованному тексту, не по
   позиции; саммари — одно неделимое поле; frontmatter — по ключам.
3. **Порт `GithubApi` + фейк в тестах.** `SyncEngine`/`RepoStore` — классы с внедрёнными
   зависимостями и `today`, не object. Предел повторов 409 — 3, дальше `Divergence`.
4. **Кэш обновляется из ответа записи**: `content.sha` → карта, `commit.sha` →
   `lastCommitSha`. Отдельный опрос ref после записи не нужен.
5. **pending-overlay в кэше**: UI читает кэш+overlay (галочка не отскакивает, офлайн видна);
   входящая дельта пропускает пути с pending либо гонит их через `ConflictRule`.
6. **Очередь**: файловый журнал `files/repo/queue/` (по файлу на операцию: тип, путь, Edit,
   baseSha, id, попытка); один drain-воркер в уникальной цепочке `repo-write`
   (`APPEND_OR_REPLACE`), внутри — цикл с `delay(1000)` между мутациями; `failure()` только
   на нашем баге, сеть/409/лимит — `retry()`. **Пуш заметок v1 — своя цепочка и приоритет:
   правки задач никогда не задерживают доставку свежей записи** (принцип 2).
7. **`inbox/` для приложения — только чтение.** Правки и удаление — лишь по обработанным
   заметкам и задачам; иначе гонка с Action.
8. **Запись только со свежим sha.** PUT без `sha` разрешён только при создании нового файла;
   404/422 = путь уехал → перечитать карту, файл не создавать (иначе воскресший дубль).
9. **Инвариант формата — идемпотентность канонизации**, а не побайтовый круговой прогон:
   `build(parse(build(parse(x)))) == build(parse(x))`, парсер принимает неканоничный ввод
   (лишние пробелы, `- [X]`, переставленные ключи, кавычки, кириллица). **Неизвестные ключи
   frontmatter сохраняются.** Правка frontmatter — построчная, тело файла не переписывается.
10. **`NoteRef`** заменяет `findDonePath`: тождество «локальная запись ↔ путь в репо» живёт в
    кэше и переживает переименование Action-ом (`renamed`/`previous_filename`, плюс запасное
    тождество по `recorded` из frontmatter, если `compare` отдал `removed`+`added`).
11. **Лента = локальные записи `NotesStore` ∪ заметки из кэша**, ключ склейки — `NoteRef`.
    Запись без сети видна в ленте со статусом и не двоится после пуша (принцип 4).
12. **UI никогда не ждёт сеть**: приложение открывается на вкладке «Заметки», лента и кнопка
    «Записать» рисуются из кэша мгновенно, синк идёт фоном; расхождение по 409 показывается
    непрерывающей плашкой в деталке, не модалкой.
13. **`RepoCache(dir)`**: json с `version` и `repo`, запись через temp+rename; битый файл,
    чужая версия или смена репо/токена → холодный старт, не исключение.
14. **Кодирование пути и Base64** — по одному месту на всё (`java.util.Base64`, minSdk 34);
    существующий `GithubClient.putFile` переводится на них же.
15. **Имя файла задачи** — `TaskFile.fileName(date, title, taken)`: транслит кириллицы,
    kebab-case, при коллизии суффикс `-2`. Чужой файл молча не перезаписывается.
16. **Сортировка задач**: приоритет P1→P3, внутри — просроченные, затем по сроку, затем без
    срока по дате создания. Сделанные — в свёрнутой секции.
17. **Состояние фильтров** — `rememberSaveable`, между запусками не живёт.

### Развилки, которые ревью оставило ведущему (решено 2026-08-26, не переоткрывать)

18. **Удаление задачи убирает ссылку на неё в заметке-источнике** тем же коммитом. Обратный
    индекс не нужен: `source:` у задачи и есть путь заметки. Иначе репо гниёт мёртвыми
    ссылками, а его смысл — читаться глазами в GitHub.
19. **Удаление заметки не трогает её задачи**, если галочка не отмечена. Их `source`
    становится висячим — приложение показывает «заметка удалена», кнопка источника
    неактивна. Чистить чужие файлы без спроса нельзя.
20. **Правка заголовка заметки файл не переименовывает.** Путь заметки неизменен после
    переноса Action-ом — иначе рвутся `source` у задач, кэш и очередь.
21. **`zipball` выкинут из скоупа.** Холодный старт — `trees?recursive=1` + чтение файлов;
    при усечении `compare` или `diverged` — свежая карта через `trees` и дочитывание **только
    файлов с изменившимся blobSha**. Причина: 302 на подписанный URL с переносом заголовка
    `Authorization` — лишняя ловушка ради одного запроса. Спека приведена в соответствие.
22. **Папки типов — первого уровня**, вложенности нет: на этом стоит относительная ссылка
    `../tasks/…` из любой папки типа.
23. **Кэш хранит тексты целиком** (личный репо — сотни файлов), сбрасывается при смене репо
    или токена. Граница пересматривается, если репо перевалит за пару тысяч файлов.
24. **Одиночный PUT — внутренняя оптимизация `RepoStore`, а не второй публичный путь.**
    Экраны не выбирают между contents API и батчем и вообще не знают про GitHub.
25. **Эталонная пара «промпт ↔ парсер»** живёт в `app/src/test/resources/action/`: заметка в
    том виде, как её оставляет Action, и порождённые задачи. Промпт меняется только вместе с
    этой фикстурой — иначе слои разъедутся молча.

## Срезы

Нарезка вертикальная: после каждого владелец видит поведение, а не отчёт о префакторе.

### Н1 — задачи видны списком *(демо: положить файл в `tasks/` тестового репо → открыть приложение → он в списке)*

`TaskFile.parse` + `NoteFile.parse/build` + `GithubApi`/фейк + `GithubClient` (readTree,
readBlob, readFile) + `RepoCache` + `RepoStore` (только чтение) + `TasksScreen` с рубриками
P1–P3, свёрнутым «Сделано» и переключателем вкладок. Полное чтение `tasks/` (без ETag и
compare — репо личный). Тесты: `TaskFile` на неканоничных фикстурах, `TaskFilter` сортировка
с `today` параметром, `RepoCache` на `TemporaryFolder` (битый json → холодный старт),
`RepoStore` на фейке порта. Смоук: чтение живого `voice-notes-test`.

### Н2 — пульт заработал *(демо: тап по чекбоксу → коммит в тестовом репо; правка полей; создание; удаление задачи; всё это офлайн — уходит при появлении сети)*

`Edit` + `apply` + `WriteQueue` + обновление кэша из ответа + pending-overlay +
`ConflictRule` + `TaskDetailScreen` (сегмент статуса, поля, подзадачи, ссылка на источник) +
создание шторкой + удаление одной задачи (contents `DELETE`, галочка по умолчанию).
Тесты: два тапа → одна операция; дельта не трогает pending; конфликт «мы приоритет, они
срок» → Merged; «оба статус» → Divergence; предел повторов; переживание убитого процесса.
Смоук: полный цикл против тестового репо, проверка `gh api` что файл изменился.

### Н3 — список наполнился *(демо: сухой прогон показывает, что мигрирует; прогон — одним коммитом; фильтры сужают список)*

`Migration.plan` + `BatchPlan` + `commitBatch` + `Registry` + `FilterChips` (проект,
приоритет, статус) со значениями из реестров и счётчиками. Миграция — **один** коммит с
сообщением `migration: tasks v2` (откат одним `revert`), идемпотентность по состоянию
заметки (чекбокс, ставший ссылкой, повторно не мигрирует), имя файла задачи детерминировано.
Тесты: `Migration.plan` на фикстуре с немигрированным чекбоксом (в тестовом репо такая
заметка есть), повторный прогон даёт пустой план; `BatchPlan` (удаление = `sha: null`,
переименование = удаление+создание). Смоук: сухой прогон и реальный на тестовом репо.

### Н4 — Action v2: задачи из разговора *(демо: прогон workflow на тестовом репо)*

Промпт в `docs/examples/process-notes.yml`: извлекать задачи в `tasks/` **после** переноса
заметки (чтобы `source:` указывал на конечный путь), ссылки вместо чекбоксов, сопоставление
с `people.md` без пополнения реестра, уникальность имён файлов задач, существующие файлы в
`tasks/` не изменять. В workflow — `pull --rebase` + повтор перед push (иначе коммит
приложения роняет job). Боевой workflow — только после утреннего подтверждения.

Критерии приёмки среза:

1. Заметка с задачами в разговоре → в `tasks/` новые файлы, в теле заметки на месте
   чекбоксов ссылки `- [Заголовок](../tasks/…md)`, чекбоксов-дублей не осталось.
2. **Ни один `source:` не указывает на `inbox/`** — только на конечный путь заметки в папке
   типа. Это ровно то, что делает ссылку «задача → заметка-источник» рабочей. Инвариант,
   на котором держится относительная ссылка `../tasks/…`: папки типов — первого уровня,
   вложенных папок в репо заметок нет.
3. **Обратная совместимость: в разговоре нет задач → заметка обрабатывается как v1** —
   секции «Задачи» нет, остальное без изменений, кроме разделения блоков саммари пустой
   строкой (без неё GitHub слепляет их в абзац; так же написана фикстура в тестовом репо).
4. Файлы, лежавшие в `tasks/` до прогона, не изменены и не перезаписаны; имена новых
   уникальны (при совпадении даты и слага — суффикс `-2`, `-3`).
5. Новых записей в `people.md` и `projects.md` не появилось; незнакомое имя осталось в
   тексте как услышано.
6. `actionlint docs/examples/process-notes.yml` зелёный.
7. Эталонная пара фикстур `app/src/test/resources/action/` сверена вручную с входом в
   тестовом репо: транскрипты совпадают с `inbox/`-исходниками побайтово, каждое поле меты
   выводится из текста разговора. После первого живого прогона она сверяется с его
   результатом **по содержимому, а не по имени файла**: имя
   `tasks/2026-08-26-podnyat-limit-retraev.md` в тестовом репо занято нарочно (blob
   `7b9f54a6…`, запись журнала 2026-08-26 03:1x), поэтому прогон обязан оставить тот файл
   нетронутым и создать `2026-08-26-podnyat-limit-retraev-2.md`; с тем же суффиксом придёт
   и ссылка на него в заметке. Расхождение ровно в этом суффиксе — пройденный критерий 4,
   а не провал сверки (правило «промпт меняется только вместе с фикстурой» — README там же).

### Н5 — лента заметок v2 *(демо: фильтры сужают ленту; правка полей заметки видна в GitHub)*

Склейка `NotesStore ∪ RepoCache` по `NoteRef`, чипы ленты (тип/проект/персона/тег/дата),
деталка заметки: поля-чипы, выбор участников из реестра, задачи ссылками. Правка **текста
саммари** — последний необязательный пункт среза, делать только если остальное зелёное.

**Долг Н1, закрываемый здесь:** `DetailScreen` создаёт `GithubClient` сам и зовёт
`findDonePath`/`readFile` мимо `RepoStore` — инвариант «UI не ходит в API напрямую» нарушен со
времён v1. Срез обязан снять это вместе со склейкой: чтение заметки идёт через фасад, прямых
вызовов клиента в `ui/` не остаётся (в коде помечено `// ponytail:`).

### Н6 — удаление заметки вместе с задачами *(демо: диалог с галочками → один коммит)*

`DeleteDialog` (по умолчанию только файл в репо), «задачи этой заметки» определяются
сканированием `source:` у задач в кэше (не парсингом ссылок в тексте), удаление аудио —
второе подтверждение и запрет для заметки, ещё не ушедшей в репо.

### Н7 — обновление не тратит лимит *(демо: два refresh подряд — второй не тратит квоту)*

ETag на ref → `compare` → `RepoDelta` → дочитывать только файлы с изменившимся blobSha;
усечённый `compare`/`diverged` → пересбор `trees` + чтение изменённых. Ручной pull-to-refresh
— всегда безусловный запрос (поведение ETag/CDN не проверено). Закрывает критерий 14.

### Н8 — за чертой утра (не ночью)

Переименование персоны по всем заметкам одним коммитом; ручное пополнение реестра персон из
предложений Claude. Дорогой и самый рискованный жест — только после приёмки.

**Порядок:** Н1 → Н2 → Н3 (ядро запроса владельца) → Н4 → Н5 → Н6 → Н7. Параллель возможна
только Н4 с Н5+ (разные слои); ночью ведём последовательно — общее дерево, один пишущий.

## Вердикты ревью замысла (2026-08-26)

Четыре оси параллельными агентами. Все находки внесены в решения LLD и нарезку выше.

- **Бизнес — CHANGES REQUESTED** (13). Ключевое: первые три среза не давали владельцу ничего
  осязаемого → вертикальная перенарезка Н1–Н3; миграция поднята рано (иначе экран задач утром
  пуст); лента не должна терять локальные записи (принцип 4); правки задач не должны
  задерживать пуш записи; удаление одной задачи вынуто из тяжёлого батч-среза; персоны и
  правка саммари — за черту; Action не второй и требует критерия обратной совместимости;
  миграция — одним коммитом с откатом через revert; нужен тестовый репо (создан).
- **LLD — CHANGES REQUESTED** (13 + мелочи). Ключевое: журнал очереди в файлах и один
  drain-воркер (WorkManager Data 10 КБ, KEEP глотает вторую операцию, APPEND рушит цепочку);
  кэш обновляется из ответа записи; pending-overlay; трёхсторонний `ConflictRule` на
  структурах; порт `GithubApi` и фейк вместо моков HTTP; `BatchPlan` отдельно от сети;
  `java.util.Base64`; идемпотентность канонизации вместо побайтового прогона; `NoteFile`
  в первый срез; реальные фикстуры API (сняты); контракт `RepoCache`; перенарезка С3/С5/С7/С8.
- **HLD — CHANGES REQUESTED** (12 + мелочи). Ключевое: единица записи — `Edit`, не текст;
  `NoteRef` вместо `findDonePath`; `inbox/` только для чтения и `pull --rebase` в workflow;
  `source:` пишется после переноса заметки; `renamed` может прийти как `removed`+`added`;
  усечённый compare — дочитывать только изменившиеся blob'ы; схема формата в одном месте и
