# ADR: задача — отдельный файл в репо заметок; реестры проектов и персон

Дата: 2026-08-26 · Статус: принято · Решения утверждены владельцем в гриллинге 2026-08-25
(Q14–Q20, Q23–Q25), карта wayfinder `nikitatrubaev-5dd`, тикет `nikitatrubaev-5dd.1` ·
Расширяет `docs/specs/2026-08-24-note-format.md` (решение Q5 «сводный список задач — v2»).

## Проблема

В v1 задача — строка-чекбокс `- [ ]` в секции «Задачи» саммари. Владельцу нужен настоящий
трекер: список задач с фильтрами по проекту, приоритету, статусу, тегу и сроку, с подзадачами
и правкой из приложения. Строку-чекбокс нельзя ни отфильтровать, ни снабдить полями — у неё
нет места под проект, приоритет и срок, а статус живёт в символе внутри чужого файла.

## Решение

**Одна задача — один `.md`-файл в папке `tasks/` репо заметок.** Имя —
`ГГГГ-ММ-ДД-слаг.md` (дата создания + слаг из сути). Frontmatter:

```markdown
---
title: Фикс ретраев очереди
project: tgsum            # слаг из projects.md; поле опускается, если проекта нет
priority: P1              # P1 высокий / P2 обычный / P3 низкий; по умолчанию P2
status: open              # open / in_progress / done
source: встречи/2026-08-24-1807-reliz-tgsum.md   # у ручных задач поля нет
created: 2026-08-25
due: 2026-08-28           # дата без времени; опускается, если срока нет
tags: [релиз]             # свободные слова, без реестра; опускается, если тегов нет
---

Свободный текст-описание (не обязателен).

## Подзадачи
- [x] Воспроизвести баг на длинной записи
- [ ] Экспоненциальный бэкофф в PushWorker
```

**Подзадачи — чекбоксы внутри файла задачи, один уровень.** Своих полей (проект, приоритет,
срок) у подзадачи нет. Апгрейд до отдельных файлов с `parent:` остаётся возможным и
механическим, если одного уровня станет мало.

**Реестры — markdown-списки в корне репо заметок:** `projects.md` и `people.md`, по строке на
запись, `- слаг — пояснение` (пояснение опционально). Правятся из приложения и руками в GitHub.

**Заметка получает поля `project` и `tags`** в frontmatter; `participants` — каноничные имена
из `people.md`. Тип заметки `задача` сохраняется: заметка — документ-источник, задача — рабочая
единица; одно порождает другое, но это разные сущности (глоссарий `CONTEXT.md`).

**Контракт Action v2:**

- извлекает задачи из транскрипта в файлы `tasks/`, а секцию «Задачи» в заметке заменяет
  ссылками на них: `- [Фикс ретраев очереди](../tasks/2026-08-25-fix-retraev.md)`;
- статус задачи живёт **только** в файле задачи — чекбоксов-дублей в заметке нет;
- сопоставляет услышанные имена с `people.md` и ставит каноничные, но **новых персон в реестр
  не добавляет** — ослышки Deepgram не должны его засорять; незнакомое имя остаётся в заметке
  как есть, решение принимает владелец в приложении;
- триггерится по-прежнему только на `inbox/**` со `status: raw`; done-заметки и `tasks/`
  Action не трогает никогда.

**Миграция:** разовый прогон по существующим done-заметкам — чекбоксы «Задач» превращаются в
файлы `tasks/` и заменяются ссылками.

## Последствия

- Правки владельца в приложении не затираются: Action работает только на raw-этапе. Плата —
  саммари не перегенерируется после ручной правки (вне скоупа v2).
- Файлов в репо становится больше (одна задача = один файл), зато каждый читается в GitHub и
  правится с телефона одной строкой.
- Незнакомые имена накапливаются в тексте заметок, пока владелец не заведёт персону руками.
- Эталон workflow `docs/examples/process-notes.yml` и рабочая копия в репо заметок меняются
  синхронно с этим ADR.

## Отклонено

- **Сводный `TASKS.md`-индекс вместо файлов** — поля приоритета и проекта негде держать,
  подзадачи не выразить, правка строки в общем файле конфликтует с каждой второй записью.
- **`tasks.jsonl` в духе beads** — удобно машине, нечитаемо человеку в GitHub; противоречит
  принципу «репо заметок читается глазами».
- **Папки по проектам** (`tasks/tgsum/…`) — перенос задачи между проектами становится
  переименованием файла; метка в frontmatter дешевле.
- **YAML-реестры** вместо markdown-списков — GitHub показывает их сырым кодом, строгий
  синтаксис ломается от лишнего пробела, а реестр — это просто список имён.
- **Реестр тегов** — тег должен рождаться на лету; список для фильтра собирается из
  встречающихся значений.
- **P0–P4 как в beads** — пять градаций для личного трекера дают трение при выборе.
